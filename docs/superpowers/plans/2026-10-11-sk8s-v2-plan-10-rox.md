# sk8s v2 Plan 10: ReadOnlyMany volumes (ROX)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Many-reader reference volumes (the genome-index use case) at persistent-disk
prices: populate a volume once, then fan out an arbitrary number of concurrent read-only
pods — no Filestore, no 1 TiB minimum. Plus the v1-style storage-class plumbing that makes
all of this (and RWX) invisible at `create_volume` time.

**User rulings (Jared, 2026-10-11 — binding):**
1. API surface is ONLY `create_volume(size, access_modes=[...])` (the param already
   exists). NO `seal_volume`, NO `rox=True` sugar, NO `":ro"` suffix on volume names —
   each explicitly vetoed.
2. Port v1's pattern: the config file carries a mode→storage-class map, written by
   `sk8s config` from the profile; `create_volume` resolves the class from the requested
   access modes when `storage_class` is not given. The user never types a storage class.
3. StorageClass creation (where needed) happens at cluster-config time, never at volume
   creation time. Autopilot ships `standard-rwx` and the PD classes; `generic` may need
   an ensure-StorageClass step (v1's `add_rwx_storage_class` equivalent).
4. Live spike BEFORE library code: the populate question is empirically open. v1's own
   test file has the ROX line commented out and replaced with RWO (jobs.main
   `test_k8s.py:127`) — v1's concurrent-reader wins were the RWX/Filestore default path.
   Nobody has prior art for populate-under-PD-CSI; the cluster rules on the design.

**Ruling update (Jared, 2026-10-11, post-spike — supersedes ruling 1's scope):**
5. Volumes are LOGICAL objects: created with a set of ALLOWED access modes; each job
   mount picks its own access mode at submission, **defaulting to read-only**; writers
   opt in (`volume_modes="rw"` or `volume_modes={"name": "rw"}` — final syntax may be
   adjusted by Jared). The library implements ROX per the spike + Google's documented
   method: an RWO primary PVC always backs the volume; `rw` mounts use it directly;
   read-only mounts of a ROX-allowed volume use a library-maintained `dataSource` clone,
   re-cloned only when a `rw` job has completed since the last clone (generation
   tracking). Consequences accepted: ro fan-outs see a point-in-time view (as of the
   last completed writer); default-ro means every writing job (scratch volumes, existing
   tests) becomes an explicit `rw` mount.
6. No `rox_storage_class`: a clone must use its source's storage class (GKE doc
   requirement), so only the RWX mapping survives in the config plumbing.

**Spec:** extends `docs/superpowers/specs/2026-10-10-sk8s-v2-design.md` §(volumes, config);
rulings above override where they conflict.

**Branch/workflow:** `feat/rox` from `version-2` (post-GKE merge 9dea5ae), clone

## Global Constraints

(All prior constraints carry: client models only, no shell=True, mypy --strict, TDD,
suite green per commit, gcloud/kubectl sanctioned for CLI/dev-docs/tests only.)

- Isolation on GKE identical to Plan 9: `KUBECONFIG=~/code/jobs/jobs.rox/.kubeconfig-gke`,
  `SK8S_CONFIG` pointed inside the clone, never the user's global files; standing cluster
  `autopilot-cluster-1` only (no cluster create/delete); everything created in GCP named
  `sk8s-*`, inventoried with teardown commands.
- Backward compatibility is absolute: a volume created with default modes
  (`("ReadWriteOnce",)`) and no configured class map behaves byte-identically to today.
  `storage_class=` stays as the explicit escape hatch and always wins.
- CI safety: everything ROX-specific that needs a real multi-node cluster is env-gated so
  the minikube CI run is unchanged; minikube-compatible parts (class resolution, mount
  wiring) get integration coverage in the normal suite.

## Review Focus

1. **The spike's findings are the design input** — Task 2+ must cite the spike report for
   every mechanism decision (mount flags, populate flow). Any library code contradicting
   the spike's observed behavior is a blocker.
2. **No behavior change for existing volumes:** RWO-only volumes must produce identical
   V1Job/PVC objects before and after this branch — pinned by unit tests that diff built
   objects against pre-branch expectations.
3. **The misleading-failure modes must be typed and hinted:** a reader fleet blocking a
   writer (multi-attach), and a forgotten read-only fan-out wedging on the second node —
   neither may surface as a silent `Pending` hang. Same bar as `JobRejected`/doctor hints.
4. **Class resolution must fail loudly when unconfigured:** RWX/ROX modes requested with
   no mapped class and no cluster default that supports them → typed error with a
   `sk8s config` hint, not a PVC stuck in `Pending`.
5. **The GKE verification reuses the standing cluster and the existing durable setup;**
   the live ROX test must prove CONCURRENT readers on ≥2 nodes (not two pods on one node).

### Task 1: live ROX spike on GKE (no library code)

**Files:** `.superpowers/sdd/<ledger dir>/spike-report.md` only (plus throwaway scripts
under a git-excluded scratch dir). Nothing in `sk8s/` changes.

The matrix, each cell with the actual YAML + observed events captured:
- [ ] (a) ROX-only PVC (`accessModes: [ReadOnlyMany]`, PD class): does dynamic
  provisioning succeed at all? If yes, can N pods on ≥2 nodes mount it simultaneously
  with no pod-level `readOnly` flags? (Force node spread, e.g. anti-affinity.)
- [ ] (b) Populate: can a ROX-only PVC ever be written under PD CSI (first rw mount
  before any RO attach?), or is populate impossible in-band?
- [ ] (c) Dual-mode PVC (`[ReadWriteOnce, ReadOnlyMany]`): provision, populate via one
  writer pod, writer completes/detaches, then N readers on ≥2 nodes — with pod-level
  `readOnly: true`, and again without it. Which combinations attach, which fail, with
  what event signatures (capture the exact multi-attach error text for Task 3's hints)?
- [ ] (d) The blocking cases: readers holding the disk while a writer starts, and a
  rw-mount fan-out — capture the exact failure signatures.
- [ ] Spike report: a decision table (which mechanism the library will use for
  populate→read; whether a writer-side flag is needed and what it must set), the raw
  evidence, and GCP/cluster cleanup verified. Ledger the design ruling.

### Task 3: logical volumes — per-mount access modes + the hidden ROX clone (rulings 5–6)

**Files:** `sk8s/volumes.py`, `sk8s/spec.py`, `sk8s/cluster.py` (JOB_OPTIONS +
diagnostics), `sk8s/errors.py`, tests.

- [ ] TDD the mount-mode API: every job mount defaults to read-only; `volume_modes="rw"`
  / `volume_modes={"name": "rw"}` opts a job's mount(s) into read-write. Pod spec sets
  `readOnly: true` on BOTH `volumes` and `volumeMounts` for ro (per the GKE doc).
  Existing writing call sites (scratch_volume docs/tests, integration suites) become
  explicit `rw` — update them; the diff of built objects for an rw mount is empty vs
  pre-branch (RF2).
- [ ] The clone machinery: a ro mount of a ROX-allowed volume resolves to the volume's
  current clone PVC (`dataSource: {kind: PersistentVolumeClaim}`, same class/size as
  the source — GKE doc requirement), created lazily and re-created when a `rw` job has
  COMPLETED since the last clone (generation tracking — annotations on the primary PVC
  record writer-completion generation; clone carries the generation it was taken at).
  Clones are labeled/owned like volumes (anchor ownership; `keep` follows the source).
  Never clone while a writer is attached (the dirty-journal/noload hazard): wait for
  the writer job's completion; bound wait, typed timeout.
- [ ] Typed diagnostics (RF3), hint text quoting the spike's verbatim signatures:
  `FailedAttachVolume … Waiting for detach … already used by pod(s)` (readers blocking
  a writer / rw fan-out) and the PVC-level `VolumeContentSource must be provided`
  infeasible event (should be unreachable through the API, but detected anyway) — both
  surface as typed errors via the watcher/CLI waiting-reason machinery, not hangs.
  Document point-in-time read semantics loudly (ro fan-out = last completed writer).
- [ ] Minikube integration: mount-mode wiring, default-ro built objects, rw round-trip,
  and — if minikube's default provisioner accepts PVC dataSource clones — a single-node
  clone lifecycle test; else unit-level fakes + mark it GKE-only. CI unchanged.
- [ ] Full suite + mypy. Commit.
