# Plan 12 — Fleet performance: kill the attachment cap, protect pods, burst to quota

**Date:** 2026-10-16 · **Author:** Claude (session with Jared) · **Target branch:** `version-2`

## Baseline and diagnosis

`wgs2-spot` (wf-p66ilh, 2026-10-16): 2 samples × 22 autosomes, 2,900 window tasks in 484
chunks of 6, all spot. Killed by request at 97.3% after **4.9 h wall**; results harvested
from the memo cache (471/484 chunks, 0 task errors, recall 0.9561 / gt 0.9902, $5.55
useful compute vs ≈$8 billed). Three measured bottlenecks, in order of damage:

1. **ROX attachment cap.** GCE read-only PDs attach to **at most 10 instances**. The
   single hidden clone serving the `wgs-ref` read-only mounts pinned the fleet at ~13
   nodes × 3 pods = **40 running** (asked for 60; quota allows 95). 21 pods sat in
   ContainerCreating for hours (one waited 2h42m, then did its work in 20 min) —
   scheduled, occupying node capacity, possibly billed.
2. **Autoscaler eviction.** sk8s sets **no `cluster-autoscaler.kubernetes.io/safe-to-evict`
   annotation** — the protect-by-default ruling exists in prose only. 4 chunks died to
   three-strikes ScaleDown bin-packing kills (not spot reclaims), and 3 workflow drivers
   died the same way earlier in the day.
3. **Serial submission and memo lookups.** One-at-a-time Job creation and one-at-a-time
   memo lookups stretch fleet ramp-up and wave turnover (ledgered twice).

Ruling this plan implements (Jared, 2026-10-16): per-CPU-second billing makes
**parallelism free** — "same cost to have a zillion CPUs that finish fast as few CPUs
that run forever." Burst to quota; tune chunk size, not width.

## Goal

Re-run the identical **unfiltered** 2-sample whole-genome benchmark (`wgs3-bench`) at
quota width with the fixes in place: **wall ≤ 2 h** (vs 4.9 h), cost ≈$6 spot, all 2,900
windows, recall ≈0.956 aggregate.

**Explicitly out of scope** (Jared): satellite/k-mer read filtering — benchmarks stay
unfiltered for now. Also out: the vCPU quota raise above ~190 (a support ticket, days of
latency; documented as the next multiplier, not blocking), delete-on-harvest cleanup, and
the rest of the cohort-ledger friction list.

## Workstream A — protect pods (clone `jobs.protect`, branch `feat/protect-pods`)

Implements the protect ruling plus its session refinement: *eviction tolerance means
surviving involuntary spot reclaim, not inviting voluntary autoscaler churn.*

- `spec.py`: `cluster-autoscaler.kubernetes.io/safe-to-evict: "false"` on **every** pod
  sk8s builds — workers, drivers, spot and on-demand alike. The annotation blocks only
  voluntary ScaleDown compaction (max cost: a node drains one chunk-length later); spot
  market preemption ignores it and remains `backoff_limit`'s job.
- `workflows.py`/`cluster.py`: detached-workflow drivers default to `backoff_limit=2`
  (three drivers died to node churn in one day; a driver death orphans the whole run).
- Tests: annotation present on worker + driver pod specs; driver backoff default; an
  explicit opt-out knob is **not** added (nobody has asked for evictable pods).

## Workstream B — Hyperdisk ML for read-only volumes (clone `jobs.hdml`, branch `feat/hyperdisk-ml`)

Hyperdisk ML is Google's answer for one-volume-many-readers: read-only attach limits in
the **thousands** (2,500 instances for ≤512 GiB) vs PD's 10. Plan-10's rulings hold:
access_modes-only API, v1-style storage-class resolution, **live spike first**.

**Spike (gates the workstream):** on the standing Autopilot cluster, by hand:
1. StorageClass `sk8s-hyperdisk-ml` (`pd.csi.storage.gke.io`, `type: hyperdisk-ml`).
2. 20 Gi PVC; populate from the existing `wgs-ref` PD via a copy pod (old ro + new rw);
   flip to ReadOnlyMany consumers.
3. Fan out ≥12 small **spot** reader pods forced onto distinct nodes; verify >10 nodes
   attach, reads are healthy, and note which machine series Autopilot provisions (Hyperdisk
   ML is machine-family-gated; if Autopilot demands a compute class, record the cost delta).

**Library change (if the spike passes):** the hidden read-only clone that serves
`access_mode: "ro"` mounts resolves its StorageClass the v1 way (config knob, default
stays `standard-rwo`); set `sk8s-cohort`'s config to the hyperdisk-ml class. Tests mock
the SC resolution; the spike is the live proof.

**Fallbacks, in order:** (1) clone fan-out — N hidden PD clones, claims round-robined,
≤10 nodes each (pure sk8s work, no GCP dependency); (2) stay capped and let Workstreams
A/C land alone. GCS FUSE is parked: it needs its own mount plumbing and an unbenchmarked
bwa-over-FUSE story.

## Workstream C — parallel submission (clone `jobs.submit`, branch `feat/parallel-submit`)

- `api._fan_out` / cluster submission: bounded thread pool (≈8) for Job creation **and**
  memo lookups; preserve Budget admission semantics (verdicts must stay serialized or
  equivalent) and the order of returned futures.
- Measure: time to submit 484 chunks before/after (baseline ramp was minutes; the memo
  harvest's 484 serial lookups took minutes on their own).

## Workstream D — benchmark and report (in `jobs.cohort`)

1. Migrate the reference: one sk8s job copies `wgs-ref` (ro) → new hyperdisk-ml volume
   (rw) — minutes, vs ~80 min of bwa re-index. Keep the old PD until the benchmark passes.
2. Rebuild the worker image from merged `version-2` (new tag = deliberate memo miss;
   update `.sk8s-cohort.toml` — the version-skew lesson).
3. `examples/cohort_wgs.py` (first commit of this file): `max_concurrent` derived from
   the Budget cap (95 today) instead of hand-picked 60; reference volume name becomes
   config/flag-selectable; `volume_wait_seconds` back to a sane value once attach is fast.
   Chunk size stays 6 — don't move two variables at once.
4. Run `wgs3-bench` (2 samples, unfiltered). Success criteria:
   - 0 FailedAttachVolume / attach-cap FailedScheduling events
   - ≥90 pods sustained Running; 0 BackoffLimitExceeded from ScaleDown
   - wall ≤ 2 h; spot cost ≈$6±1; 2,900/2,900 windows; recall ≈0.956
5. Report: wgs3 vs wgs2 in the cohort artifact (wall, effective width, waste gap),
   ledger updated, old `wgs-ref` PD deleted after success.

## Order and budget

0 → {A ∥ B-spike ∥ C} → B-library → D. Merges gated on self-review + green tests, per
standing swarm rules. Spend: spike <$1, benchmark ≈$7, hyperdisk storage pennies —
≤$15 against the $600 cap. Expected math at width 95: 484 chunks × ~17.4 min ÷ 95 ≈
**~1.5 h wall**, same CPU-seconds as 4.9 h at width 40.

## Risks

- **Hyperdisk ML × Autopilot × spot** is the real unknown (machine-series gating, compute
  classes, spot availability). The spike answers it for <$1 before any library code.
- Version skew between driver image and local sk8s (bit us once already) — image rebuild
  is a numbered step, not an afterthought.
- Billing of ContainerCreating pods remains unreconciled; the benchmark's zero-queue
  design makes it moot going forward.
