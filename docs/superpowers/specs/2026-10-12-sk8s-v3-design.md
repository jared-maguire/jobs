## 0. The first principle and the acceptance test

> **Your outputs are supposed to be pure functions of your inputs — that's what
> "science" means.**

Everything in v3 serves the twelve-line target interaction (the bar napkin, top
of `docs/v3-wishlist.md`). A feature that doesn't move toward those lines is out
of scope. The corollary of the principle: *execution is cache-miss
materialization*; impurity is a thing you declare, not a thing that happens to
you; a result is an artifact hash with a derivation trail.

## 1. Scope and relationship to v2

v2 is the engine room and is **kept**: the job layer (typed V1Job building,
watcher, futures), stores, RBAC/profile/doctor, GKE integration, volumes (incl.
ROX clones), services (frozen), the CLI, the skill. v3 is built *above* it in
two tiers:

- **Tier 1 — shippable incrementally on v2's API** (several pieces built the
  night of this spec; see §12): the v2.x fixes, `explain`/`--json`/`dry_run`,
  QC gates + pilot, `sk8s data describe`, then artifacts/CAS + memoization.
- **Tier 2 — the architectural break** (needs its own plan cycle): the workflow
  IR + durable interpreter, task cards, two-tier execution, autosizing, spot,
  the autonomy policy. Two breaks that evolution cannot deliver politely are
  authorized by the greenfield analysis: **build-system execution semantics**
  and **no-pickle task boundaries** (pickle survives as dev-mode sugar).
  `sk8s.run(lambda: 42)` remains working forever.

Non-goals for v3: multi-cluster federation, EKS (parked until opted in), a
hosted service, any UI beyond the CLI + JSON surfaces (the "resident computer"
is an agent harness consuming these surfaces, not a product sk8s ships).

## 2. Architecture overview

```
 you / the agent ("the computer")
        │  natural language
        ▼
  frontends: eager Python (sugar) · Python builder · Starlark/IR (agents)
        │  emit
        ▼
  workflow IR  ──verify──▶ type/budget/contract checks (client-side, instant)
        │  submit (a record, not a process)
        ▼
  durable interpreter (in-cluster driver v2→v3) ── event log in the store
        │  materialize cache misses
        ▼
  v2 job layer (unchanged) ── pods ── artifacts in the CAS
```

State lives only in the cluster (k8s objects) and the store (CAS + manifests +
event logs). Every client — human Python session, agent, CLI — is a stateless
view. Nobody's laptop is ever load-bearing.

## 3. The artifact layer (CAS + refs)

The data plane, per wishlist item 8 (rulings: staging localization; both
content-addressed and browsable). Normative details:

### 3.1 Layout

```
<store>/artifacts/cas/sha256/<hh>/<hash>          # the bytes, immutable
<store>/artifacts/index/sha256/<hh>/<hash>.json   # manifest: locations, size,
                                                  #   checksums, provenance
<store>/workflows/<wf>/artifacts.json             # the workflow's reference set
                                                  #   (the GC mark roots)
```

Published objects live wherever the user says (`gs://bucket/runs/...`) with
custom metadata `sk8s-artifact-sha256`, `sk8s-produced-by` pointing back.

### 3.2 API

```python
a = sk8s.artifact("gs://bucket/in/s1.fq.gz")   # reference; hashes lazily on
                                               # first staging; pinned to
                                               # (uri, generation, sha256)
def align(fq: Path, out: sk8s.OutDir) -> sk8s.Artifact:
    ...                                        # fq staged in; real POSIX path
    return out / "s1.bam"                      # declared output, staged out

bam = sk8s.run(align, a)                       # Artifact
bam.publish("gs://bucket/runs/oct/s1.bam")     # the refs layer; durability
```

- Inputs typed `Artifact` are **staged** to pod-local scratch pre-exec (sized
  via ephemeral-storage requests; generic ephemeral volumes above a threshold);
  the function receives `Path`s. Outputs returned as `OutDir`-relative paths
  are hashed-while-uploading into the CAS.
- `publish` is **move-by-default** (Decision A3): the ref becomes the hash's
  recorded location; CAS key is GC'd. `publish(..., copy=True)` keeps both.
  Because refs are last-writer-wins (§3.3 rule 3), a moved hash's bytes live
  at an overwritable path — so **staging-in always verifies the sha256 while
  streaming** (it is hashing anyway): a mismatch is a typed integrity error
  and staging falls back to the hash's other recorded locations. Memo hits
  can therefore never silently serve overwritten bytes.
- Staging inherits the store-credentials model: on `store_env` stores (MinIO)
  worker-side staging has the same nested-credentials gap the skill documents
  for nested submits — scoped to `gs://`/`k8s` until that gap closes.
- External inputs: hash on first staging, cached keyed by (uri, generation) —
  GCS generations / S3 ETags+version-ids detect in-place overwrites; a changed
  generation is a *new artifact* (correct cache miss).

### 3.3 Concurrency and GC

- All index/manifest writes use optimistic preconditions:
  GCS `ifGenerationMatch` (0 = create-if-absent), S3/MinIO
  `If-None-Match`/`If-Match` on PUT, ConfigMap `resourceVersion` — as NEW
  store methods; ConfigMapStore's existing delete+recreate `put` is not
  CAS-safe and is never a fallback (spike implication #5). **Live-verified
  2026-10-12** (spike-conditional-writes.md; condensed verdicts in Appendix B):
  exactly-one-winner create-if-absent and correct optimistic read-modify-write
  on all three backends; ≤~5 retries/success under 10-way single-key
  contention (GCS/ConfigMap ~5, MinIO ~0.9), so all retry loops are bounded
  and jittered.
- **Normative rules forced by the spike findings:**
  1. **The full-object sha256 is always computed in the upload stream** —
     client- or worker-side. ETags are never identity (multipart ETags are
     md5-of-part-md5s and layout-dependent; multipart `ChecksumAlgorithm`
     checksums are COMPOSITE, not full-object). GCS has no sha256 at all.
  2. **GC never relies on conditional delete** — S3/MinIO accepts
     `DeleteObject(IfMatch=…)` and silently ignores the condition. Safety
     comes from the mark-and-sweep structure: record-intent-first manifests
     make in-flight references reachable; the age floor covers the
     registration window; the sweeper RE-CHECKS reachability immediately
     before each delete (the mark set alone is a TOCTOU hazard — a hash
     re-registered after the mark pass must not lose its bytes); and doctor
     gains a store-conformance probe for the conditional-write primitives,
     since other S3 implementations may differ in either direction. (The
     "identical bytes" argument excuses only *create* races, never deletes.)
  3. **Refs (published paths) are last-writer-wins**, like any human-named
     file — S3 `CopyObject(IfNoneMatch)` silently ignores the precondition, so
     create-if-absent on publish destinations is not portable and is not
     promised. The CAS layer, not the refs layer, is where identity lives.
  4. **The index manifest is the authoritative provenance record.** Object
     metadata (`sk8s-artifact-sha256`, `sk8s-produced-by`) is best-effort
     decoration: S3 metadata cannot be updated under a precondition at all,
     and on GCS a content re-upload silently WIPES custom metadata (verified),
     so metadata is always (re)set after content lands and never trusted as
     the only copy of anything.
  5. Generation pinning is **detect, not recover**: on unversioned buckets an
     old GCS generation reads as 404/412, and S3 identical-overwrite keeps the
     same ETag (A→B→A defeats `IfMatch`). Pins detect change for cache
     correctness; they do not promise retrieval of old bytes. (Bucket
     versioning upgrades this, deliberately out of scope for v3.0.)
- GC is mark-and-sweep: roots = every workflow's `artifacts.json` (written
  BEFORE first use — the record-intent-first rule) + all published refs;
  unreachable CAS objects older than an age floor are deleted by `clean()`.
  No live refcounts, ever.
- Node-local cache (Tier 2, with the executor work): CAS objects cached on
  node SSD keyed by hash; a 100GB BAM downloads once per node. Until then,
  staging cost is paid per pod and the spec accepts it.

### 3.4 Memoization (collapses into the above)

`sk8s.run(f, a, memo=True)` (and config `memo = true`): key =
sha256(canonical(function bytecode+closure consts) + input artifact hashes +
image identity + relevant job options). Image identity = the resolved digest
when the runtime can obtain one, else the tag with a documented mutability
caveat (a re-pushed tag is a cache-correctness leak the user accepted by
re-pushing — the build-your-own doctrine already discourages it). Before submitting, look up
`artifacts/memo/<key>` → an output-manifest hit returns the prior Artifacts
without running anything (the napkin's "$0 tomorrow"). Non-artifact arguments
participate via their pickle hash with a documented stability caveat; the
clean path is artifact-typed inputs. Failed runs never write memo entries.
Cache invalidation = don't pass `memo=` or bump an explicit `memo_salt=`.

## 4. The workflow IR (Tier 2 — the architectural core)

A workflow is **data**: a typed, content-addressed graph. Node kinds:
`task` (a task card invocation or dev-mode pickled function), `map` (fan-out
over a list or an upstream output, with batch/concurrency/pilot attributes),
`gate` (expectation over upstream results; semantic failure), `choose`
(conditional on upstream values), `subworkflow`, and `decision` (an
agent-in-the-driver hook: an LLM call whose prompt/inputs/output are
event-logged — auditable, replayable; disabled unless the autonomy policy
allows it). Edges carry typed values: artifacts, JSON scalars/structures.

Properties: the IR serializes to JSON; its hash names it (`wf-7f3a` in the
napkin is a prefix of it); `verify(ir)` runs client-side with no cluster —
type-checks edges against task-card contracts, totals resource/budget claims,
rejects unbounded fan-out without a budget. `plan(ir)` renders the human/agent
preview (the napkin's second line) including cost estimate. The IR admits
dynamic sub-graphs: a `map` over a runtime value expands at execution,
event-logged, bounded by the budget.

Frontends:
- **Eager Python (humans, default)**: today's API. `submit_workflow` compiles
  the driver function into a one-`task` IR (so ALL execution flows through the
  interpreter — one code path; the tethered path becomes sugar per the
  removals ruling).
- **Builder (agents and humans)**: explicit `wf = sk8s.Workflow(); s =
  wf.task(align, fq); wf.gate(...)` — emits IR directly, no magic.
- **Starlark frontend (agents)**: **feasible, live-verified** (spike, 2026-10-12;
  Appendix B.2). Implementation: `starlark-pyo3` (starlark-rust 0.13; wheels for
  current Python; deterministic across 200 runs and hash seeds; `open`/`import`/
  `time`/`random`/`os` unreachable; rustc-style spans with "did you mean" — the
  error quality agents need; a 10k-node fan-out evaluates in ~7ms (~120ms
  with JSON extraction — return JSON, never raw Python objects)). Design-arounds the spike forces, all normative:
  1. **Runtime branching lives in explicit IR nodes (`choose`/`map`), never in
     Starlark control flow over runtime values** — a fan-out template body
     evaluates ONCE on a placeholder, so branching on the item inside it
     silently takes one branch (verified live). Starlark is for *plan-time*
     structure; the IR is for *run-time* dynamics. NOTE: the binding exposes no
     host-defined types, so the placeholder CANNOT defend itself — enforcement
     is (a) a lint pass over the emitted template that rejects `if`/`str`/index
     on placeholder values, and (b) a small CEL-like expression language for
     runtime conditions inside IR nodes (both per the spike's recommendations).
     Host-side placeholder types (a Rust shim, or starlark-go) are an open
     question, not a plan of record.
  2. Evaluation runs under the binding's cancel-callback with a wall-clock
     limit (~1s verified) — there is no step/memory limit in the binding, and
     the cancel callback stops CPU spins but NOT memory balloons (OOM panic,
     verified): untrusted definitions evaluate in a subprocess under
     RLIMIT_AS. The binding is a single-maintainer dependency behind a ~100
     line adapter — keep it swappable.
  3. No module-level mutable registration (loaded modules freeze): `task()`
     etc. return values the caller composes; the workflow is the evaluation's
     return value.
  The deterministic-Python-replay (Temporal) model is NOT pursued for v3
  (Decision A9): the spike removed the tooling doubt that motivated it, and
  plan-time Starlark + runtime IR nodes keeps replay trivial (the IR, not user
  code, is what replays).

## 5. The durable interpreter

The v2 detached driver generalizes: an in-cluster process that *interprets IR*,
appending every decision/observation to an **event log** in the store
(`workflows/<wf>/events/NNNNNN.json`, append = create-if-absent on the next
sequence number; a retried append that hits 412 against its own earlier write
must read back and compare — appends are idempotent by content, per the
spike's lost-ack hazard). Crash/restart = replay the log, resume at the
frontier.
`kill`/`resume` are log operations. The interpreter holds no state a replay
can't rebuild — same discipline as v2's "reconstructible from labels", now
with history instead of forensics. Eager-mode and notebook sessions get the
same durability by being one-task IRs.

Scheduling concerns owned here (Tier 2): spot/preemptible classes with
preemption-aware retry; resource autosizing (per-task-card observations →
prediction with margin; OOM → resubmit at 2× is the v3.0 floor); straggler
re-execution for maps; the two-tier executor — k8s Jobs for normal tasks, a
resident-worker queue tier for short tasks (measured floor, Appendix B.2:
3.0s median per Job, ~3.3 jobs/s single-node ceiling, vs 40ms resident-pod
exec — route tasks with expected runtime under ~10–30s to the resident tier).

## 6. Task cards (Tier 2)

A task card is a versioned, content-addressed declaration: name, container
image (digest), command/entrypoint template or python callable ref, typed
inputs/outputs (artifact kinds + JSON schema for scalars), resource model
(request = f(input sizes) with fitted coefficients + margins), declared
impurities (none | seed:<param> | network | time), QC expectations bundled as
default gates, docs string for agents. Cards live in-repo
(`sk8s-cards/*.json|py`) and/or a store prefix; the IR references cards by
hash. The capability library (bwa, samtools, GATK…) is cards + images,
community-shareable — nf-core's role, with machine-checkable contracts.

## 7. Verification of answers

- **Gates** (shipped Tier 1 as `expect=`/`ExpectationFailed`): callables over
  results, run worker-side, failing semantically. In the IR they are `gate`
  nodes and compose with maps (the napkin's S23 quarantine = per-item gate
  failure with the rest proceeding).
- **Pilot** (shipped Tier 1 as `pilot=n`): first n to completion through their
  gates before the fleet. In the IR, an attribute of `map`.
- **Equivalence declarations** (Tier 2): a task card may declare what "same
  result" means for caching/verification — exact-bytes (default), canonical
  form (e.g. sorted BAM), or tolerance comparators. The tolerance is a
  scientific claim made explicit (the bar ruling: small deltas = move on,
  large = investigate — now a declared threshold with an `investigate` event).
- **Golden runs** (Tier 2): `verify(ir, against=golden_manifest)` — run on a
  truth set, compare declared outputs through the equivalence comparators.

## 8. Observability

`explain` (shipped Tier 1): the one-call picture. In Tier 2 it becomes a query
over the event log (cheaper, historical, exact). `--json` everywhere (shipped).
Cost accounting: rough estimates Tier 1 (requests × duration × price constant);
exact per-workflow accounting when the event log lands. `fut.logs()` /
`sk8s logs --follow` upgrade with the interpreter.

## 9. Guardrails and the autonomy policy

- **Budgets** (small, early Phase 2): `budget=` on workflow submission — max
  concurrent pods, max cpu-hours, max estimated spend; typed `BudgetExceeded`
  at admission or mid-run (interpreter-enforced in Tier 2; client-enforced
  best-effort before that).
- **Sandbox**: `sk8s sandbox create` = namespace + profile apply + SK8S_CONFIG
  file + default budget, auto-reaped by age. One command for the isolation
  pattern every agent in the v2 build maintained by hand.
- **Autonomy policy** (Tier 2, with `decision` nodes): a config-file schema —
  spend ceilings, forbidden verbs (delete published artifacts, cross-project
  egress), approval-required actions. The interpreter refuses what the policy
  forbids; `decision` nodes record policy context in the event log. Trust is a
  config file, not a vibe.

## 10. The data catalog

Tier 1 ships `sk8s.describe` (format sniffing, cohort summaries — the napkin's
"Found 48 samples"). Tier 2 grows it into a catalog: described facts cached as
artifacts keyed by (uri, generation); lineage joins `describe` output to the
CAS provenance; user-attached semantics (`sk8s data annotate <uri> ...`) stored
as manifest fields. The catalog is derived state — always reconstructible by
re-describing; never authoritative.

## 11. Removals and demotions (per the wishlist rulings)

- The laptop-tethered path becomes sugar over one-task workflows (Tier 2, with
  the interpreter; API unchanged).
- `serve`/services: kept, frozen. No new service features in v3.
- ConfigMap store: demoted to dev/simulator duty in docs and defaults
  (`sk8s config` warns when a multi-node profile selects store k8s); still
  fully supported for the inner loop.
- Cloudpickle at task boundaries: demoted to dev-mode (eager API) once task
  cards exist; the IR's `task` nodes reference cards, not pickles, except the
  explicitly-marked dev node kind.

**Deferred beyond this spec's phases (visible, not forgotten):** wishlist
item 3 (cron + bucket-event triggers — arrives naturally with the interpreter
and the store notifications), item 5 (GPUs as first-class requests), item 7's
fast dev loop and the LocalCluster-as-simulator upgrade, and item 6's
dashboard — §1's "CLI + JSON only" non-goal narrows item 6 to `explain` +
cost accounting for v3.0 (Decision A10); a web dashboard is a later, separate
decision of Jared's.

## Appendix A — Decisions made without oversight (for Jared's morning review)

- **A1** Memoization is opt-in (`memo=True`/config), not default-on, for v3.0
  — purity isn't yet declared per-task, and silent staleness scares me more
  than silent recompute. Flip the default when task cards declare impurities.
- **A2** Artifact staging reserves pod ephemeral storage = 2× declared input
  sizes (headroom for outputs) unless overridden; generic ephemeral volume
  above 50Gi. Numbers are judgment, revisit with data.
- **A3** `publish` moves by default (single copy; CAS entry retired to a
  location pointer). `copy=True` for keep-both.
- **A4** `expect=` runs worker-side (not client) so gates hold for detached
  workflows and nested submits. As SHIPPED (PR #95), the worker serializes the
  result, runs the gate, then writes ONE blob — a normal result on pass, an
  `expect_failed` blob (still carrying the rejected value) on fail. Storing
  before gating was rejected in review: a crash during the gate would leave a
  good-looking result the client trusts over the failed pod. Evidence still
  survives via the `expect_failed` blob + `keep_results`.
- **A5** `pilot=` blocks the remainder on the pilot (no speculative overlap)
  — simplicity first; overlap is an interpreter-era optimization.
- **A6** The `decision` node (LLM-in-the-driver) is specced but gated behind
  the autonomy policy and OFF by default. It is the most philosophically loaded
  feature in here; it ships only with the policy layer.
- **A7** Tier assignments themselves (what ships tonight vs. waits for the IR)
  — driven by the napkin-value-per-risk ordering, not by any ruling.
- **A8** Cost estimates use a single documented $/cpu-hour constant per
  provider profile rather than live pricing APIs (predictable, offline,
  roughly right; exactness arrives with the event log).
- **A9** The Temporal-style deterministic-Python-replay model is dropped in
  favor of plan-time Starlark + runtime IR nodes, on the spike's evidence
  (tooling doubt removed; replay stays trivial because the IR, not user code,
  replays). Revisit only if the IR's dynamic nodes prove too cramped in
  practice.
- **A10** Wishlist item 6 (observability) is narrowed for v3.0 to `explain` +
  cost accounting under §1's CLI+JSON-only non-goal; a web dashboard is a
  separate, later decision that remains Jared's.

## Appendix B — Spike evidence (condensed; full reports in the plan ledger)

### B.1 Conditional writes (live, 2026-10-12: GCS, MinIO RELEASE.2026-09-22, ConfigMap)

| Primitive | GCS | S3/MinIO | ConfigMap |
|---|---|---|---|
| Create-if-absent | ✅ `ifGenerationMatch=0` (412 loser) | ✅ PUT `IfNoneMatch="*"` (412), also on CompleteMultipartUpload | ✅ create (409 loser) |
| Optimistic RMW | ✅ generation precondition | ✅ `IfMatch=etag` | ✅ `resourceVersion` (must be IN the write) |
| Conditional delete | ✅ works (unused by design — GC never relies on it) | ❌ **silently ignored** | ✅ works (unused by design) |
| Create-if-absent on copy | ✅ rewrite+`ifGenerationMatch=0` | ❌ **silently ignored** | n/a |
| Metadata preconditions | ✅ metageneration patch | ❌ none (self-copy REPLACE only, ETag unchanged) | ✅ via resourceVersion |
| Server sha256 | ❌ (crc32c/md5 only) | ✅ single-part FULL_OBJECT; ❌ multipart (COMPOSITE) | n/a |
| Content overwrite keeps metadata | ❌ **wipes it** | n/a | n/a |
| Old-version read (unversioned) | 404/412 | same-ETag A→B→A defeats IfMatch | opaque equality only |

Contention datum: 10 concurrent writers on one key converge correctly at ~5
(GCS/CM) / ~1 (MinIO) retries per success. Exception classes per backend are
tabulated in the full report for the library to catch precisely.

### B.2 Starlark feasibility + k8s Job floor (live, 2026-10-12)

**Starlark:** `starlark-pyo3` 2026.1.2 (starlark-rust 0.13) is the only strong
option (starlark-go: no current wheel; pure-python `starlark` 0.6.0: new,
unreviewed, and it name-clashes with starlark-pyo3's top-level package — pick
ONE dependency). Verified: byte-deterministic across 200 runs/4 hash seeds;
sandbox holds (no fs/network/time/random); typed annotations check at runtime
and statically; errors carry spans + suggestions; 10k-node eval 7ms (84ms with
json.encode; ~750ms if converted to Python objects — return JSON). Gaps: no
step/memory limits (a runaway loop OOM-panics; the cancel callback works and
aborted at 1.00s — mandatory), frozen modules forbid implicit registration, and
the dynamic-fanout trap: a map template body runs once on a placeholder, so
item-dependent branching inside it silently misbehaves → runtime dynamics
belong in IR nodes (§4 rule 1).

**Job floor (minikube, 1 node, warm image):** 3.0s median/Job (p90 3–4s; ~2s
status propagation + ~1.5s container start); 50 concurrent Jobs = 15.1–15.5s
(~3.3 jobs/s ceiling; per-job latency ~10s under that load). Resident-pod exec:
168ms via kubectl (≈100ms kubectl startup), 40ms via the Python client, 0.4ms
in-pod. Full data: spike-starlark-and-floor.md.
